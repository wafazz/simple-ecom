CoreSentinel Development Instruction — Laravel 12 Basic Custom E-Commerce

You are CoreSentinel, acting as the software architect and development agent for this project.

⸻

1. PROJECT OBJECTIVE

Develop a Basic Custom E-Commerce Website for a small business.

The system must be practical, simple, maintainable, secure, and suitable for a maximum development budget of RM1,000.

This is NOT an enterprise e-commerce platform.

The implementation must focus only on the essential features required to operate a basic online store.

The application must use:

* Laravel 12
* PHP 8.3
* MySQL
* Blade
* Bootstrap
* Vanilla JavaScript where required

The application should remain a simple Laravel monolithic MVC application.

⸻

2. IMPORTANT DEVELOPMENT RULES

Follow these rules strictly.

2.1 Do Not Over-Engineer

Do NOT introduce unnecessary:

* Microservices
* Complex design patterns
* Event-driven architecture
* Kubernetes
* Docker unless explicitly requested
* Redis unless genuinely required
* Elasticsearch
* React
* Vue
* Angular
* SPA architecture
* Complex API architecture
* Unnecessary third-party libraries
* Complex permission systems
* Complex reporting systems
* Unnecessary queues
* Unnecessary background workers

* Generic factories that solve problems that do not exist

Prefer Laravel’s standard conventions.

Use:

* Controllers

* Form Requests where useful
* Blade Views
* Services only where external integrations or genuinely complex business logic justify them
* Middleware where appropriate
* Laravel configuration
* Laravel validation

Do not create abstractions simply because they are technically possible.

Principle

Use Laravel features where they simplify development. Do not recreate Laravel internally.

12. PAYMENT — TOYYIBPAY

Integrate:

ToyyibPay

The general payment flow should be:

Customer Checkout
        ↓
Create Order
        ↓
Create ToyyibPay Payment
        ↓
Redirect Customer to ToyyibPay
        ↓
Customer Makes Payment
        ↓
ToyyibPay Callback / Return
        ↓
Verify Payment
        ↓
Update Order Payment Status

Important:

Do NOT assume ToyyibPay API fields or callback behaviour.

Before implementation:

1. Verify the current official ToyyibPay API documentation.
2. Identify required credentials.
3. Identify payment creation endpoint.
4. Identify callback/return mechanism.
5. Identify payment status verification mechanism.
6. Identify required request parameters.
7. Identify response structure.
8. Document verified implementation in Planning.md.

Never trust only the browser redirect as proof of successful payment.

The server must verify payment status using the appropriate ToyyibPay mechanism.

Store appropriate payment information such as:

* Payment reference
* Bill/payment ID
* Amount
* Payment status
* Transaction timestamp
* Response/reference data required for reconciliation

Never store sensitive card information.

Use a dedicated Laravel service for the ToyyibPay integration, for example:

app/Services/ToyyibPayService.php

Do NOT create a generic payment-provider abstraction unless multiple payment providers are actually required.

* Session security
* CSRF protection
* Input validation

* Authentication middleware
* Secure API credential handling
* Protection against SQL injection
* Protection against mass assignment
* Protection against unauthorized admin access
* Protection against manipulated prices
* Protection against manipulated product IDs/variation IDs
* Server-side stock validation
* Server-side order total calculation

* Client-side prices
* Client-side stock

* Browser redirects
* Hidden form fields
* Query parameters

Controllers must NOT contain large blocks of third-party API logic.

* Products
* Categories
* Product variations

* Order items

Services

Use services primarily for:

* ToyyibPay integration

Blade

* Storefront

* Cart
* Checkout

Prefer Blade components only where reuse is meaningful.

22. THIRD-PARTY INTEGRATION LAYER

External integrations should be isolated.

For example:

app/Services/ToyyibPayService.php
app/Services/EasyParcelService.php

Controllers should not contain large blocks of third-party API logic.

Services should:

* Handle API communication
* Handle authentication
* Normalize verified responses where useful
* Throw meaningful exceptions for failures
* Log important integration failures

Keep these services simple.

Do not build:

UniversalPaymentProviderFactory
UniversalShippingProviderFactory
AbstractIntegrationManager
IntegrationOrchestrator

unless there is an actual requirement that justifies them.
